# VERITAS V2.1 — Evidence Intake & Integrity Foundation

**Document status:** Implementation specification
**Target branch:** `v2.1-evidence-intake`
**Foundation:** `v2.0.0-foundation` / commit `1da4f91`
**Migration target:** `0003`
**Principle:** Preserve evidence integrity and human accountability; automate intake mechanics, not forensic conclusions.

---

## 1. Objective

VERITAS V2.1 introduces the first real digital-evidence lifecycle capability on top of the verified V2 identity and authorization foundation.

The objective is to allow an authenticated, authorized user to register an evidence item, place its original bytes into an isolated quarantine location, compute cryptographic integrity values while the bytes are written, validate basic file characteristics without interpreting the evidence, preserve the accepted original, and record the resulting custody and audit events.

V2.1 is an **evidence intake and integrity foundation**.

It is not an examination engine and must not claim to determine whether evidence is genuine, manipulated, forged, AI-generated, or forensically reliable.

The V2.1 workflow is:

```text
Authenticated User
        ↓
Case authorization
        ↓
Evidence registration
        ↓
Quarantine
        ↓
Streamed byte intake
        ↓
SHA-256 + SHA-512
        ↓
Basic type/signature validation
        ↓
Preservation
        ↓
Custody event
        ↓
Canonical AuditEvent
        ↓
Evidence available for later examination
```

## 2. Scope

V2.1 implements:

* authenticated evidence intake for authorized Cases;
* extension of the existing canonical `Evidence` entity;
* immutable `EvidenceObject` records representing preserved byte objects;
* isolated local quarantine and preserved storage;
* streaming upload with an evidence-specific size limit;
* SHA-256 and SHA-512 calculation during intake;
* declared media type and server-detected media type;
* basic file-signature validation for supported formats;
* immutable storage references;
* evidence integrity metadata;
* initial chain-of-custody events;
* organization and Case authorization using the existing V2 security model;
* canonical `AuditEvent` integration;
* frontend evidence-intake and integrity views;
* adversarial security and regression tests;
* Docker persistence isolated from the web container.

V2.1 must reuse the existing V2:

* User;
* Organization;
* OrganizationMembership;
* Role;
* RoleAssignment;
* UserSession;
* authentication;
* authorization;
* Case;
* Evidence;
* EvidenceProfile;
* AuditEvent;
* request ID;
* structured error envelope;
* PostgreSQL/Alembic architecture;
* same-origin frontend/API architecture.

## 3. Non-goals

The following are explicitly excluded from V2.1:

* OCR;
* NLP;
* computer vision;
* deepfake detection;
* AI-generated-content detection;
* audio analysis;
* video analysis;
* PDF semantic extraction;
* document semantic extraction;
* malware execution or sandboxing;
* automatic forensic conclusions;
* automatic findings;
* AI agents;
* LLM APIs;
* external AI services;
* URL-based evidence ingestion;
* remote URL fetching;
* shell execution;
* arbitrary command execution;
* public evidence upload;
* public signup;
* public verification;
* evidence deletion;
* overwriting preserved evidence;
* evidence editing;
* automated chain-of-custody transfers;
* OIDC;
* MFA;
* production object storage implementation;
* distributed rate limiting;
* WORM storage;
* signed evidence manifests;
* external immutable audit export.

A file being accepted by V2.1 means only that VERITAS successfully received and preserved the bytes under the implemented intake rules. It is **not** a forensic authenticity verdict.

### 4.1 Identity

Use the existing authenticated `User` and `UserSession`.

Do not introduce another user/person identity model.

### 4.2 Authorization

Use `backend/app/domain/roles.py` as the single policy source.

Every evidence operation must verify:

1. active authenticated User;
2. active Organization membership;
3. authorized Case scope;
4. required evidence capability.

Frontend visibility is never a security boundary.

### 4.3 Case

The Case's Organization remains authoritative for tenancy.

### 4.4 Audit

Use the existing `AuditEvent`.

Do not create an `EvidenceAudit`, `CustodyAudit`, `SecurityAuditLog`, or second audit database.

Evidence lifecycle events may appear in the canonical Audit stream while chain-of-custody events remain a dedicated domain projection for the evidence workflow.

### 4.5 EvidenceProfile

`EvidenceProfile` remains the canonical structured evidence-profile projection.

Computed integrity values must have one source of truth:

```text
EvidenceObject
    ↓
EvidenceProfile projection
```

Do not store duplicate independent copies of hashes.

## 5. Evidence lifecycle

### 5.1 Logical Evidence lifecycle

The existing `Evidence.state` remains the lifecycle state of the logical evidence item:

```text
REGISTERED
    ↓
WITHDRAWN
```

V2.1 does not change the semantics of those existing states.

### 5.2 EvidenceObject lifecycle

`EvidenceObject` has its own immutable intake/preservation state:

```text
QUARANTINED
    ↓
PRESERVED
```

or:

```text
QUARANTINED
    ↓
REJECTED
```

Allowed transitions:

```text
QUARANTINED → PRESERVED
QUARANTINED → REJECTED
```

No API may transition:

```text
PRESERVED → anything
REJECTED → anything
```

A preserved object cannot be edited, replaced, or overwritten.

A future re-acquisition must create a new immutable EvidenceObject rather than modifying an existing one.

## 6. Canonical evidence data model

The existing `Evidence` entity remains the logical evidence record.

V2.1 extends it only where required for intake.

Existing fields remain:

```text
id
case_id
label
evidence_type
description
state
created_at
updated_at
created_by
updated_by
```

No second logical evidence table may be introduced.

### 6.1 EvidenceObject

Create:

```text
backend/app/domain/models.py
```

entity:

```text
EvidenceObject
```

Purpose:

Represent exactly one captured byte object associated with one logical `Evidence`.

Suggested public identifier:

```text
EOBJ-001
```

Fields:

```text
id                      internal UUID
public_id               stable public identifier
evidence_id             FK → evidence.id
case_id                 FK → cases.id
organization_id         FK → organizations.id

original_filename       client-declared filename metadata
declared_media_type     client-declared media type
detected_media_type     server-detected media type
byte_size               number of accepted bytes

sha256                  lowercase hexadecimal SHA-256 digest
sha512                  lowercase hexadecimal SHA-512 digest

storage_key             opaque storage reference
state                   QUARANTINED | PRESERVED | REJECTED

validation_status       pending | accepted | rejected
validation_note         controlled metadata only

acquired_at             server-generated UTC timestamp
acquired_by             authenticated actor public ID

preserved_at            UTC timestamp, nullable
preserved_by            authenticated actor public ID, nullable

created_at
updated_at
created_by
updated_by
```

Rules:

* internal UUID is never returned to the client;
* public ID is stable and immutable;
* `storage_key` is never an operating-system absolute path;
* the original filename is metadata only and can never become a filesystem path;
* SHA-256 and SHA-512 are immutable after the object reaches `PRESERVED`;
* `byte_size` is server-computed;
* `acquired_at` and `acquired_by` are server-derived;
* clients cannot submit their own actor identity;
* clients cannot submit their own preserved timestamp;
* clients cannot supply or overwrite a storage path;
* clients cannot provide trusted cryptographic hashes as authoritative values.

If the client supplies a hash in metadata for future verification purposes, it must be treated only as an untrusted declared value and must not replace the server-computed digest.

V2.1 does not need client-supplied hashes.

## 7. EvidenceObject relationship rules

`EvidenceObject` belongs to one logical `Evidence`.

Recommended relationship:

```text
Evidence 1 ──── * EvidenceObject
```

This permits future re-acquisition without rewriting history.

The first preserved object is not automatically marked as "the truth".

A later object represents another captured byte object and receives a separate immutable identity and separate hashes.

The UI must clearly identify each object by its own public ID.

Do not silently replace one object's bytes with another object's bytes.

V2.1 must not add a duplicate hash document table.

Example conceptual projection:

```text
Integrity
  status: Verified

  attributes:
    SHA-256
      basis: computed
      value: <digest>

    SHA-512
      basis: computed
      value: <digest>
```

The exact attribute representation must reuse the existing `ProfileAttribute` contract.

A profile value is a projection of the canonical `EvidenceObject`, not a second persisted source.

The word `Verified` means only that the declared integrity attributes were computed by the implemented reproducible procedure.

Recommended UI wording:

```text

```

not:

```text

```

## 9. Quarantine architecture

All uploaded bytes must enter quarantine before preservation.

Required logical layout:

```text
EvidenceStorageRoot/
    quarantine/
    preserved/
```

The quarantine area must not be:

* inside `frontend/dist`;
* inside the nginx web root;
* publicly routable;
* directly downloadable from nginx;
* executable;
* reachable from a browser URL.

The storage service owns all file access.

The API must never construct paths by concatenating a client-supplied filename.

## 12. Docker storage boundary

The evidence storage directory must be mounted only into the backend container.

Conceptually:

```text

    /var/lib/veritas/evidence
           ↑
      evidence volume
```

The web/nginx container must not mount the evidence volume.

The evidence volume must therefore not be able to become an accidentally served static directory.

The Docker stack should use a dedicated named volume, for example:


The exact Compose name may be generated by the selected project name.

Do not use the existing PostgreSQL volume for evidence.

## 14. Upload architecture

V2.1 must use a streamed raw-byte upload rather than loading the entire evidence file into application memory.

Use a three-stage workflow.

### Stage A — Register

```http
POST /api/v1/cases/{case_id}/evidence-intake
```

Request body:

```json
{
  "label": "Phone export",
  "evidence_type": "document",
  "description": "Synthetic intake test",
  "original_filename": "phone-export.pdf",
  "declared_media_type": "application/pdf"
}
```

Rules:

* authorization is checked before creating the record;
* `case_id` is resolved server-side;
* Organization scope is resolved server-side;
* actor is derived from the authenticated session;
* `acquired_at` is generated by the server;
* status starts as `QUARANTINED`;
* a new `Evidence` and `EvidenceObject` are created;
* no evidence bytes exist yet.

Response contains:

```text
evidence.id
evidence_object.id
state
upload endpoint
created_at
```

No token, password, raw session value, or storage path is returned.

### Stage B — Upload raw bytes

```http
PUT /api/v1/cases/{case_id}/evidence/{evidence_id}/content
Content-Type: application/octet-stream
```

The server:

1. authenticates the request;
2. authorizes Case access and intake capability;
3. resolves the target Evidence server-side;
4. confirms the EvidenceObject is still `QUARANTINED`;
5. creates/opens a server-generated quarantine file;
6. streams request chunks;
7. updates byte count;
8. updates SHA-256;
9. updates SHA-512;
10. rejects the stream once the maximum is exceeded;
11. never executes or interprets file content;
12. atomically records the resulting byte count and digests only when the complete stream succeeds.

The implementation must not read the entire request into memory.

### Stage C — Finalize

```http
POST /api/v1/cases/{case_id}/evidence/{evidence_id}/finalize
```

The server:

1. authenticates;
2. authorizes;
3. confirms upload completion;
4. validates basic file signature/type;
5. records detected media type;
6. compares declared and detected type;
7. assigns `accepted` or `rejected`;
8. for accepted objects, atomically moves the object from quarantine to preserved storage;
9. changes state to `PRESERVED`;
10. records `preserved_at` and `preserved_by`;
11. creates custody events;
12. creates canonical AuditEvents;
13. exposes the object as preserved.

For a rejected object:

```text
QUARANTINED → REJECTED
```

The quarantine bytes must be securely discarded by the storage service after the database state records the rejection.

The rejection itself must be auditable.

---

## 15. Upload failure behavior

An interrupted or failed stream must never become `PRESERVED`.

Examples:

```text
client disconnect
request timeout
body too large
write error
hashing error
storage error
```

must leave the logical object non-preserved.

The implementation must not fabricate a digest for incomplete bytes.

If a complete byte stream was written but finalization was never performed, the object remains `QUARANTINED`.

An operational cleanup mechanism may remove stale quarantine files later, but it must never remove a preserved object.

---

## 16. Atomic preservation

Preservation must be atomic from the application's perspective.

The implementation should:

```text
write quarantine temp/object
        ↓
complete stream
        ↓
validate
        ↓
flush/close
        ↓
atomic move/rename into preserved storage
        ↓
persist PRESERVED state
```

Do not expose a partially written object as preserved.

Do not reuse a preserved filename/object key.

Do not overwrite an existing preserved object.

A storage collision is an error, not an overwrite opportunity.

---

## 17. Filename handling

`original_filename` is metadata only.

It must:

* have a strict maximum length;
* be UTF-8 safe;
* have control characters rejected or normalized;
* never be used directly as a path;
* never be used as a shell command argument;
* never determine the storage key.

Directory traversal strings such as:

```text
../../secret
..\..\secret
C:\secret
/secret
```

must never become filesystem paths.

The application must treat filenames as untrusted metadata.

---

## 18. Media-type handling

There are two separate values:

```text
declared_media_type
detected_media_type
```

`declared_media_type` comes from the intake metadata and is untrusted.

`detected_media_type` is determined server-side.

V2.1 performs only basic signature/magic-byte detection for supported common formats.

At minimum, support a deliberately bounded initial registry appropriate to the product's expected inputs, such as:

```text
PDF
JPEG
PNG
GIF
WAV
MP3
MP4
ZIP-based document containers
plain text
```

The implementation may extend this registry only when it has an explicit deterministic signature rule and tests.

Do not invoke a full content parser merely to identify a type.

Do not attempt to prove semantic validity.

Do not claim a type is genuine because its magic bytes are correct.

If the declared and detected types disagree:

```text
validation_status = rejected
```

unless the type has an explicitly documented safe compatibility rule.

No silent correction is permitted.

---

## 19. File signature validation

Signature validation is a basic intake safety mechanism.

It does not constitute forensic examination.

The validator must:

* inspect only the minimum required leading bytes;
* never execute content;
* never invoke interpreters;
* reject malformed known signatures where appropriate;
* return a deterministic detected type;
* remain isolated from later semantic analysis.

The supported signature registry must live in one dedicated module.

Do not scatter magic-byte rules across API route files.

---

## 20. Hashing

Every accepted preserved object must have both:

```text
SHA-256
SHA-512
```

The hash must be calculated over exactly the accepted byte sequence.

The algorithm must be fed incrementally while the upload stream is written.

Do not:

```text
write the entire file
→ load the entire file into RAM
→ hash it later
```

The preferred flow is:

```text
chunk
 → write chunk
 → SHA-256.update(chunk)
 → SHA-512.update(chunk)
```

The final digest is recorded only after successful completion.

Digest representation:

```text
lowercase hexadecimal
```

Expected lengths:

```text
SHA-256 = 64 hexadecimal characters
SHA-512 = 128 hexadecimal characters
```

Database constraints or application validation must reject invalid digest lengths.

---

## 21. Hash immutability

Once an object becomes `PRESERVED`:

```text
sha256
sha512
byte_size
storage_key
original_filename
declared_media_type
detected_media_type
acquired_at
acquired_by
preserved_at
preserved_by
```

must be immutable.

No ordinary API may update these values.

No evidence update endpoint may mutate them.

If future verification recalculates a hash, it must create a separate verification record/event rather than modifying the original digest.

## 23. Custody immutability

`EvidenceCustodyEvent` is append-only.

No update API.

No delete API.

No direct ORM mutation.

PostgreSQL must enforce immutability at the database layer for the custody table, following the same defense-in-depth philosophy already used for `AuditEvent`.

Application-level listeners remain useful for SQLite tests.

The PostgreSQL trigger must reject:

```sql
UPDATE evidence_custody_events ...
DELETE FROM evidence_custody_events ...
```

### Event 1

### Event 2

```text

```


## 31. Duplicate/retry behavior

V2.1 must explicitly define retry semantics.

Registering evidence twice creates two logical Evidence records unless an explicit future idempotency mechanism exists.

Re-uploading bytes to an already-preserved object is forbidden.

Finalization of an already-preserved object must be safe and deterministic:

```text
HTTP 409
```

or another consistent conflict response.

The API must never silently replace preserved bytes on retry.

## 37. Storage access model

The API must not provide a generic download endpoint in V2.1 unless the authorization and content-disposition policy are explicitly implemented and tested.

The preferred V2.1 behavior is:

* store evidence privately;
* expose metadata and integrity information;
* defer controlled evidence retrieval/download until the retrieval policy is deliberately designed.

If a later read endpoint is introduced, it must:

* require authenticated Case authorization;
* never serve through a static public path;
* use `Content-Disposition: attachment`;
* use a safe content type;
* never execute content;
* generate an AuditEvent for retrieval if retrieval is part of the product policy.

## 40. Request-size security

The server must enforce the evidence-specific limit during streaming.

It must not trust only:

```text
Content-Length
```

because a client may omit or falsify it.

The implementation must count actual received bytes.

When:

```text
bytes_received > VERITAS_MAX_EVIDENCE_BYTES
```

the server must stop processing and reject the intake.

No oversized object becomes preserved.

---

## 41. Memory security

The implementation must not read the entire evidence object into RAM.

All evidence bytes must be processed in bounded chunks.

Tests must include a large synthetic object that verifies bounded-memory behavior through the chosen implementation mechanism.

The exact chunk size is an implementation detail and must be centralized rather than repeated as magic numbers.

---

## 42. File-system safety

The storage layer must ensure:

* storage root exists or is created safely;
* quarantine and preserved directories are separated;
* path components are server-generated;
* no symlink traversal is accepted where the platform permits symlinks;
* existing files are never overwritten;
* directory traversal is impossible through client metadata;
* quarantine failure cleanup cannot delete a preserved object's path.

Where supported by the runtime, file creation should use exclusive creation semantics.

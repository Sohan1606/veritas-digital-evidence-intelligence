# VERITAS V2/V2.1/V2.2/V2.3 identity, access, evidence-intake, evidence-retrieval and examination threat model

**Scope:** identity, sessions, Organization membership, role assignment, authorization to V1 case/read projections, V2.1 Evidence intake/storage/custody, V2.2 retrieval and integrity verification of preserved EvidenceObjects, V2.3 examination (Method → Analysis Run → Observation), and canonical security events. This is a description of implemented controls and their tested limits—not a claim of external penetration testing, forensic certification, or security certification.

## Assets and trust boundaries

- Canonical User identity, provisioned credentials, Organization memberships, Role assignments, and session records.
- Existing Case records and child Evidence/EvidenceProfile plus V2.1 EvidenceObject bytes, digests, custody records and audit metadata, the V2.2 retrieval/verification events derived from them, and V2.3 Analysis Runs and the Observations and events they produce.
- The existing append-only `AuditEvent` table, used for domain, identity and security events; append-only `EvidenceCustodyEvent` records.
- Trust boundaries: browser ↔ same-origin proxy ↔ FastAPI ↔ PostgreSQL and backend-private evidence filesystem; local account provisioning is an operator action, not a public API.

## Threats and controls

| Threat | Asset / attack surface | Implemented control | Automated evidence | Residual limitation |
|---|---|---|---|---|
| Stolen or invalid session credential | Session cookie presented to API | 48-byte random opaque cookie; only SHA-256 digest stored; DB lookup; status, revocation and expiry checked for every protected request; HttpOnly, SameSite=Strict and Secure in production; logout revokes server record | `test_login_uses_opaque_http_only_session_cookie_and_audits_success`, `test_expired_and_revoked_sessions_are_rejected`, `test_logout_requires_csrf_and_invalidates_session_replay` | A stolen, still-valid cookie can be replayed until logout, disablement or expiry. There is no MFA, device binding, anomaly detection, or remote OIDC provider in this version. Production must use HTTPS end-to-end to the trusted proxy. |
| Session replay / fixation | Login, browser cookies, logout | Fresh unpredictable session per successful login; no client-chosen session ID; logout invalidates server-side record; disabling a User revokes its live sessions | `test_logout_requires_csrf_and_invalidates_session_replay`, `test_disabled_user_session_is_revoked_immediately` | Database rollback/restore can reintroduce old session state if operational recovery is mishandled. |
| Cross-identity browser cache reuse | Same-tab logout/login, shared resource paths and requests still in flight | Frontend GET cache is session-identity scoped, cleared before identity changes and at logout; old requests cannot populate a later identity scope; logout clears `veritas.activeCase` | Frontend `drops User A's ready CASE-001 resource on logout and fetches a new User B response` regression test | This protects against accidental client-side reuse, not a hostile browser, memory inspection, or authorization bypass. Server-side authorization remains mandatory. |
| Brute-force attempts | `/api/v1/auth/login` | Provisioned accounts only; Argon2 verification including a dummy hash for unknown/disabled accounts; same generic credential error; per-source-IP failure buckets; configured lockout/window; stale buckets deleted after 24 hours; request/body/input limits | `test_invalid_disabled_and_unknown_users_have_same_login_error`, `test_repeated_invalid_credentials_trigger_persistent_rate_limit`, `test_auth_validation_errors_do_not_echo_password_or_username` | Distributed sources can evade a per-IP limit. When running behind a proxy, configure `VERITAS_TRUSTED_PROXY_IPS` to an exact trusted proxy IP/CIDR and have that proxy overwrite `X-Real-IP`; otherwise all requests may share the proxy address. Rate limits can also cause a shared-IP denial of service. An edge rate limiter is recommended. |
| IDOR / guessed public identifiers | Case path parameters and all case-child routes | Every case request resolves its Case server-side and checks capability against active organization membership and a role assignment; child lookups also constrain by the authorized Case; case audit independently requires `case_audit:read`; denied and nonexistent Cases produce the same 404 envelope | `test_case_scoped_role_grant_prevents_idor_cross_case_and_unknown_case`, `test_case_audit_requires_its_explicit_case_capability`, `test_non_demonstration_case_is_invisible_in_demo_mode`, existing V1 cross-case Evidence/Profile tests | Role scope is one Case at a time except an explicitly provisioned Auditor with `case:read:any`. The current product has one migration-provisioned Organization; organization lifecycle/administration is not exposed in the UI. |
| Cross-case or cross-organization leakage | Case list, Evidence/Object URLs, graph and audit endpoints | Case list only includes authorized Cases; case-specific role and Organization ID are checked; evidence, EvidenceObject, custody, finding, claim and profile IDs are queried within the resolved Case; security audit filters canonical `AuditEvent.organization_id` against organizations where the principal holds `security_audit:read` | `test_case_scoped_role_grant_prevents_idor_cross_case_and_unknown_case`, `test_organization_membership_is_required_even_with_a_case_assignment`, `test_security_audit_is_organization_scoped_and_excludes_global_unknown_login`, V1 case API tests | Query timing and aggregate request volume have not been independently side-channel tested. |
| Privilege escalation / role bypass | Admin role assignment/status endpoints; direct HTTP requests | Backend capability dependencies, session-bound CSRF checks, Organization-scoped target-user lookup, case-scoped grants, self-role assignment denied, self-disable denied; Administrator/Auditor cannot be granted or removed through the console (operator CLI only); disabled Users lose sessions | `test_administrator_role_management_is_scoped_csrf_protected_and_audited`, `test_non_admin_cannot_view_or_mutate_identity_directory`, `test_disabled_user_session_is_revoked_immediately` | A compromised Administrator can grant non-privileged operational roles to other Users in the Administrator's Organization; every such change is audited. Privileged role assignment is an out-of-band operator action and depends on host/database access controls. No multi-party approval workflow exists. |
| Malicious role assignment | Authenticated admin role grant/revoke | Explicit role-to-capability map; case scope required for console-assignable roles; privileged roles are excluded from console; self-grants denied; changes recorded in canonical Audit | `test_administrator_role_management_is_scoped_csrf_protected_and_audited` | No dual-control approval, expiry date, or just-in-time assignment. CLI operator actions must be governed externally. |
| Frontend visibility bypass | Modified browser, direct URL/API calls | Frontend hides navigation by returned capabilities, but every protected backend route independently enforces authentication, capability and Case scope. Admin endpoints reject unauthenticated/non-admin calls | `test_non_admin_cannot_view_or_mutate_identity_directory`, `test_case_scoped_role_grant_prevents_idor_cross_case_and_unknown_case`, V1 direct API tests | The frontend is not a security boundary. A hostile browser can inspect data already delivered to it; session-scoped cache clearing is only an accidental-reuse defense, and server authorization remains authoritative. |
| Demo Case disclosure of V2.1 metadata | V2.1 intake detail, custody and existing Evidence Profile projection on demonstration Cases | No V2.1 intake, object detail or custody reads on any demo Case, even for authenticated Case roles; anonymous demo profile uses only its V1 profile fields, not preserved-object projections; V1 Evidence listing/Profile behavior remains available | `test_demo_cases_cannot_create_v21_evidence_objects`, `test_demo_viewer_cannot_read_v21_intake_metadata`, `test_demo_viewer_cannot_read_v21_custody_events`, `test_demo_profile_omits_v21_object_hashes`, `test_v1_synthetic_demo_evidence_and_profile_remain_available` | Other V1 synthetic Evidence/Profile fields remain public by design in demo mode; demo data must remain synthetic and must not contain real EvidenceObjects. |
| Unauthorized Evidence intake or guessed object identifier | Intake/detail/finalize/custody routes and Case/Evidence/Object IDs | Every route first resolves the authenticated Case and active Organization membership, then checks its explicit capability; child records are constrained to that Case; Administrator identity privileges do not imply evidence access | `test_read_only_roles_and_identity_admin_do_not_gain_evidence_access`, `test_inactive_user_and_wrong_case_are_rejected`, `test_organization_membership_is_required_even_with_a_case_assignment`, existing cross-case tests | Query timing and aggregate access patterns were not independently tested; browser hiding is not a security control. |
| Resource exhaustion or oversized uploads | Raw EvidenceObject content request | Upload is consumed as a bounded stream; server counts actual bytes and enforces `VERITAS_MAX_EVIDENCE_BYTES` even when Content-Length is absent or inaccurate; temporary/quarantine content is discarded on limit/failure; normal request limit is not enlarged for files | `test_streaming_limit_uses_actual_bytes_and_cleans_partial_upload`, `test_zero_byte_upload_has_standard_hashes_and_finalization_is_one_way`, `test_digest_file_uses_bounded_reads` | The default nginx ceiling is 100 MiB and may be lower than a raised backend limit; deployments must coordinate both. Network disconnect behavior and container/runtime resource limits have not been independently exercised. |
| Malicious, malformed or mislabeled file content | Uploaded, untrusted bytes and declared media type | The application computes hashes over streamed bytes and inspects at most a bounded leading prefix using deterministic coarse signatures; mismatches and unsupported binary signatures are rejected; no archive extraction, rendering or semantic parsing occurs | `test_supported_basic_signature_results`, `test_signature_mismatch_and_unsupported_binary_are_rejected`, `test_zip_compatibility_is_coarse_and_does_not_claim_document_identity`, `test_invalid_signature_is_rejected_and_quarantine_is_discarded` | No malware scanning, content disarm, full-file parser, archive inspection, format-specific structural validation or forensic interpretation is implemented. Signature acceptance is not authenticity or safety certification. |
| Storage path traversal, symlink following, overwrite or partial preservation | Local EvidenceStorage files and opaque storage keys | Keys are generated server-side and strictly validated; exclusive creation/no-follow flags, regular-file checks, private directories, separate quarantine/preserved areas, no-replace publication and directory fsync are used; storage paths/OS errors are not exposed | `test_local_storage_creates_exclusively_and_preserves_atomically`, `test_storage_rejects_path_like_keys`, `test_storage_rejects_symlinked_private_directories`, `test_storage_failure_and_invalid_metadata_are_sanitized` | Local filesystem/host administrators remain trusted; these controls do not make storage WORM or tamper-proof. Docker mount isolation and persistence are verified only by running `scripts/qa/v2_2_runtime_check.py`, not by static inspection. |
| EvidenceObject or custody-event mutation | ORM state, database rows, preserved bytes | Lifecycle transitions are constrained; preserved metadata cannot be updated; EvidenceCustodyEvent is append-only in ORM and has PostgreSQL trigger protection; storage publication does not overwrite an existing destination; re-acquisition creates a new object | `test_custody_and_preserved_object_orm_records_are_immutable`, `test_zero_byte_upload_has_standard_hashes_and_finalization_is_one_way`, `test_postgresql_custody_trigger_rejects_update_and_delete` (PostgreSQL-only) | The PostgreSQL trigger test runs only against a PostgreSQL test database. A privileged host/database operator can still alter files, disable triggers or rewrite the database; no WORM, signed manifest, external hash chain or independent storage verification exists. |
| Malformed authentication request | Login body, path/query input, cookies | Pydantic length/shape limits, request-size middleware, structured validation errors omit submitted input; cookie values are treated as opaque strings and only hashed for lookup | `test_auth_validation_errors_do_not_echo_password_or_username`, existing hostile-path/body-size/error tests | Fuzzing coverage is bounded to automated tests; no external parser audit has been performed. |
| Sensitive error leakage | Validation, DB/ORM/framework failures | Existing structured error envelope; generic 500; no traceback/exception message sent to clients or included in JSON structured logs; route-template logging, no query/body/cookie logging | Existing `test_unhandled_error_is_generic_and_correlated`, `test_validation_errors_never_echo_input`, `test_log_formatter_drops_unapproved_fields`, `test_access_log_uses_route_template_without_query` | Database driver or infrastructure logs outside VERITAS are not controlled by this application. Operators must protect and review those logs separately. |
| Password/credential exposure | Login responses, DB, audit, logs | Password hashes use `argon2-cffi`; raw passwords are only accepted at the login/provisioning boundary; raw session and CSRF values are not returned in JSON; audit stores metadata only; session token is not logged or stored raw | `test_login_uses_opaque_http_only_session_cookie_and_audits_success`, `test_auth_validation_errors_do_not_echo_password_or_username`, `test_administrator_role_management_is_scoped_csrf_protected_and_audited` | Passwords must be entered over TLS in production. Out-of-band CLI terminal/process/host security is an operator responsibility. |
| CSRF against authenticated writes | Admin mutations and logout | `SameSite=Strict` cookies plus separate session-bound CSRF cookie; non-GET authenticated actions require matching `X-CSRF-Token` header and stored hash; CSRF denial uses canonical Audit | `test_logout_requires_csrf_and_invalidates_session_replay`, admin test's missing-CSRF mutation assertion | XSS can act as the signed-in user; CSP is defense-in-depth, not proof of XSS absence. Deployment-specific browser origins must be configured narrowly. |
| Audit alteration or disclosure | Security and case audit APIs, database | Security activity is appended to existing `AuditEvent`; no duplicate audit store; nullable `organization_id` is the authoritative tenant association; security audit requires `security_audit:read` and filters to that capability’s organization memberships; case audit requires `case_audit:read`; PostgreSQL migration trigger rejects UPDATE/DELETE; ORM listeners reject updates/deletes; API filters credential-like metadata keys | `test_security_audit_is_organization_scoped_and_excludes_global_unknown_login`, `test_case_audit_requires_its_explicit_case_capability`, `test_audit_events_cannot_be_updated_through_orm`, `test_audit_events_cannot_be_deleted_through_orm`, and `test_audit_events_append_only_in_postgresql` (trigger test runs only on PostgreSQL) | SQLite tests cannot prove the PostgreSQL trigger. Unknown-login, anonymous/system, or ambiguous multi-Organization events remain `organization_id = NULL`; they are deliberately omitted from all organization-scoped reads, and V2 provides no global platform-event reader. A database superuser can disable triggers or rewrite storage; no independent WORM service, signed hash chain, or external audit export is implemented. |
| Unauthorized retrieval or verification; guessed identifiers | `GET …/content`, `POST …/verify`, Case/Evidence/Object IDs | Both routes require authenticated `evidence:read` for a non-demonstration Case before any resolution or storage access; Evidence is constrained to the Case and the object to both; every denial (role, Case, Organization, demonstration, guessed or cross-Case id) is masked as not found and recorded as `authorization.denied`; non-PRESERVED objects are a `409`; `POST` requires the session-bound CSRF token | `test_every_authorized_role_retrieves_the_exact_bytes`, `test_administrator_is_denied_and_masked_as_not_found`, `test_wrong_case_wrong_organization_and_guessed_identifiers_are_not_found`, `test_demonstration_cases_expose_no_retrieval_to_anyone`, `test_csrf_is_required_and_a_failure_changes_nothing`, `test_denied_callers_get_not_found_never_unavailable` | Anyone holding `evidence:read` on a Case can retrieve and verify all its preserved objects; there is no per-object access control or per-user rate limit. |
| Reading something other than the preserved bytes (quarantine, alternate copy, symlink, special file) | `EvidenceStorage.open_preserved_object` | Only preserved storage is opened, by a server-held opaque key; quarantine is never a fallback; symlinked roots/directories and symlinked object files are refused (`O_NOFOLLOW`); non-regular files are refused; `O_NONBLOCK` keeps a FIFO from blocking a worker thread; descriptors are closed on every failure path | `test_a_quarantine_copy_is_never_a_fallback_for_a_missing_preserved_object`, `test_a_symlinked_object_file_is_not_followed_even_with_identical_bytes`, `test_a_named_pipe_in_place_of_the_object_is_rejected_without_blocking`, `test_a_failing_fstat_does_not_leak_the_file_descriptor` | The FIFO and descriptor tests fail against the V2.1 `_open_existing`; V2.1 deployments had that weakness. Windows has no `O_NOFOLLOW`; the final-component symlink refusal is not provided there. |
| Content sniffing, script execution or header injection from retrieved bytes or corrupted metadata | `Content-Type`, `Content-Disposition` of the retrieval response | `Content-Disposition: attachment` with a deterministic name from the public id (never `original_filename`); `Content-Type` only from the closed set of detected media types, else `application/octet-stream`, no charset asserted; global `nosniff`, `no-store` and `default-src 'none'` CSP; values are never taken from client-controlled request data | `test_hostile_database_metadata_never_reaches_response_headers`, `test_response_headers_are_safe_and_deterministic`, `test_every_detectable_media_type_is_in_the_served_allow_list` | Bytes are attacker-controlled by definition; a consumer that opens a retrieved file in an unsafe viewer is outside this control. |
| Memory or disk exhaustion through retrieval or verification | Large preserved objects, slow or abusive clients | Reads are bounded by 64 KiB chunks; nothing buffers an object or writes a temporary copy; no database connection is held during storage I/O or while a client reads slowly; nginx does not spool the response | `test_a_large_object_streams_in_bounded_chunks_with_bounded_memory` (peak traced memory while streaming 40 MiB), `test_reads_are_bounded_and_the_handle_is_closed`, `test_no_database_connection_is_held_during_storage_io`, `test_a_slow_download_holds_no_database_connection_and_does_not_block_others` | Verification reads and hashes the whole object for every request; concurrent requests are limited only by the worker thread pool. No rate limiting. |
| Modified, truncated, expanded or replaced preserved bytes going unnoticed | Preserved files on the evidence volume | Independent recomputation of byte count, SHA-256 and SHA-512 against the immutable intake values; every outcome is audited; retrieval stays available so the current bytes can still be examined | `test_every_tamper_is_a_mismatch_with_a_full_comparison`, `test_any_single_recorded_value_disagreeing_is_a_mismatch`, `test_mismatch_leaves_retrieval_enabled_and_is_not_sticky` | Detection happens only when someone verifies; it does not prevent modification, and it cannot say why a difference exists or whether the bytes were genuine before intake. A writer who can also alter the recorded digests in the database defeats it. |
| Storage failure misreported as tampering (or as success) | Missing, unreadable or failing storage | A comparison is made only from a complete successful read; any open or read failure is `UNAVAILABLE`, never `MISMATCH`; a partial read is never compared; retrieval returns a sanitized `503` or aborts the connection; nothing records a retrieval that did not complete | `test_unreadable_preserved_objects_are_unavailable_never_a_mismatch`, `test_a_read_failure_after_partial_data_is_unavailable_not_a_mismatch`, `test_a_read_failure_mid_stream_aborts_without_an_event`, `test_a_storage_outage_is_reported_honestly_and_fully_recovers` | `UNAVAILABLE` does not distinguish a transient outage from a missing object. A premature end of file without an error is indistinguishable from truncation and is a `MISMATCH`. |
| Unaudited release or audit forgery | `evidence.object.retrieved`, `evidence.object.integrity_verified` | Retrieval commits its event before the final chunk is released; a failed audit write returns an error and no result or complete copy; each verification has its own event; events carry metadata only and are append-only (ORM guards; PostgreSQL triggers) | `test_audit_is_committed_before_the_final_chunk_is_released`, `test_failed_audit_withholds_the_final_chunk_of_a_multi_chunk_object`, `test_a_database_timeout_during_verification_fails_closed_and_recovers`, `test_each_verification_records_its_own_complete_metadata_only_event` | A reader who disconnects before the final chunk leaves no retrieval event yet may hold most of the object; only the access log shows it. The event records release to the transport, not client receipt. A database superuser can still tamper with audit storage. |
| Leakage of bytes, paths, storage keys or credentials through responses, logs or audit | Error envelopes, headers, audit `details`, log lines | Sanitized storage errors (no path or OS text); audit and logs carry identifiers and digests only; the Content-Disposition name is derived from the public id; frontend keeps no bytes in state | `test_no_path_storage_key_or_credential_leaks_in_any_response`, `test_a_storage_error_message_carrying_a_private_path_never_reaches_a_client`, `test_successful_retrieval_records_exactly_one_metadata_only_event` | Digests in audit details identify content; they are metadata by design. |
| Open redirect or other-host requests from the frontend API client | `api/client.ts` | One shared same-origin path check rejects absolute and protocol-relative forms (`//host`, `/\host`, tab/newline tricks) for every client function | `every client function refuses … including protocol-relative forms` | Defense in depth: call sites already build paths under `/api/v1/`. |
| Privilege confusion: a role that should not examine starts or changes a run (Administrator, Reviewer, Auditor, Custodian, anonymous or demonstration viewer) | `POST …/analysis-runs`, `…/cancel`, `…/retry` | `examination:execute` is held only by INVESTIGATOR and RESEARCHER (one map, `domain/roles.py`); the route requires an authenticated identity and a non-demonstration Case; Case authorization and CSRF run first; a denial is a masked 404 with an `authorization.denied` event; the service refuses demonstration Cases again | `test_examination_capabilities_are_assigned_only_by_the_central_role_map`, `test_the_execute_capability_is_named_only_where_it_is_defined_and_enforced`, `test_everyone_else_cannot_change_a_run`, `test_an_authorized_executor_still_cannot_execute_on_a_demonstration_case`, `test_every_state_changing_request_requires_the_session_csrf_token` | Capability assignment is an operator/administrator decision; a user who legitimately holds the capability can queue any number of runs (no per-user quota). |
| Probing or exhausting private storage through unauthorized or ineligible requests | Request path before the worker | Authorization precedes every other step; eligibility is decided from the database; the object is only opened and closed (never read) once an authorized, eligible, non-replayed request is about to commit | `test_ineligible_requests_from_authorized_users_do_not_touch_storage`, `test_unauthenticated_requests_are_rejected_before_anything_else`, `test_everyone_else_cannot_change_a_run` | An authorized, eligible creation opens the object once to confirm it is readable. |
| Duplicate or concurrent execution (double click, network retry, two workers, a stalled worker) | `analysis_runs` creation and claiming | Unique `(case_id, created_by, idempotency_key)` with a request fingerprint decides replay vs conflict in the database; a claim is a compare-and-set (`FOR UPDATE SKIP LOCKED` on PostgreSQL); each claim stamps `started_at`, which every later write repeats, so a worker that lost its run cannot publish | `test_concurrent_identical_requests_create_exactly_one_run`, `test_the_same_key_for_a_different_request_is_a_conflict`, `test_concurrent_workers_never_claim_the_same_run`, `test_two_workers_racing_for_one_run_produce_one_execution`, `test_a_worker_that_lost_its_run_cannot_publish_anything` | Fencing relies on a claim timestamp (microsecond resolution); host clock skew shifts stale detection by the skew. |
| A run attributed to the wrong EvidenceObject, or Observations about bytes that are not the preserved object | `analysis_runs.evidence_object_id`; the reader | Composite foreign key `(evidence_object_id, evidence_id, case_id)`; service resolution inside Case → Evidence → EvidenceObject; execution-time re-resolution; the reader compares the bytes read with the recorded byte count and SHA-256/SHA-512 and fails the run on any difference | `test_a_run_cannot_name_an_object_of_another_evidence_item`, `test_a_run_cannot_name_an_object_of_another_case`, `test_every_run_names_the_exact_object_when_evidence_has_several`, `test_bytes_that_differ_from_the_recorded_intake_values_fail_closed`, `test_storage_faults_fail_the_run_with_a_distinct_sanitized_code` | The gate detects a difference from the intake record; it cannot say why and says nothing about the bytes before intake. |
| A failed or cancelled run that looks complete, or partial results | Publication of Observations | Completion, Observations and audit are one transaction; completion requires no pending cancellation; a failed run publishes nothing and carries a fixed message per code | `test_a_failure_while_publishing_leaves_no_observation_and_no_completion`, `test_a_failure_writing_the_completion_event_publishes_nothing`, `test_a_cancel_that_arrives_before_the_completion_commit_wins_and_nothing_is_published`, `test_cancel_racing_the_worker_never_yields_an_inconsistent_run` | None known beyond database availability. |
| Rewriting or deleting execution history | `analysis_runs` rows | Lifecycle table (`domain/lifecycle.py`) checked before each compare-and-set, an ORM guard, CHECK constraints, and a PostgreSQL trigger that forbids delete, request rewrites, changes to finished runs and invalid transitions | `test_every_transition_outside_the_table_is_refused`, `test_what_a_run_was_asked_to_do_is_immutable`, `test_postgres_refuses_deleting_a_run`, `test_postgres_refuses_rewriting_what_a_run_was_asked_to_do`, `test_postgres_refuses_invalid_transitions_and_any_change_to_a_finished_run` | SQLite (tests only) has no trigger. A database superuser can alter any table. |
| Evidence bytes treated as instructions, or a Method reaching files, shells, URLs or the database | Method execution | A Method receives only a chunk iterator and validated parameters; the examination package imports no process, network or filesystem module and never evaluates or opens; the binary Method counts bytes and never decodes them | `test_the_examination_package_imports_no_process_network_or_filesystem_api`, `test_the_examination_package_never_evaluates_opens_or_spawns`, `test_examination_uses_no_process_or_network_capability_at_run_time`, `test_the_reader_exposes_no_path_key_or_handle_to_a_method` | Methods are trusted code reviewed with the release; there is no sandbox for untrusted code because none is accepted. |
| Leakage of bytes, paths, storage keys, idempotency keys or exception text through audit, failure messages, logs or responses | Audit `details`, `failure_message`, logs, responses | Audit carries identifiers and state only; failure text is one fixed sentence per code; logs carry only the exception type; responses never carry keys, fingerprints or paths | `test_audit_events_carry_only_the_documented_metadata`, `test_failure_audit_and_state_carry_codes_never_exception_text`, `test_no_response_discloses_a_path_a_storage_key_or_evidence_bytes`, `test_an_unexpected_method_error_fails_closed_without_leaking_its_text` | Public identifiers (Case, Evidence, EvidenceObject, run) are metadata by design. |
| Memory or disk exhaustion by a large object, or by copies | Worker I/O | Bounded 64 KiB reads, a 256-bin histogram (O(1) memory), byte and wall-clock limits, no temporary or duplicate copy, nothing written under the evidence root | `test_bytes_are_read_once_in_bounded_chunks_and_never_all_at_once`, `test_memory_stays_bounded_while_a_large_object_is_examined`, `test_examination_never_writes_to_evidence_storage_or_makes_copies` | No per-user queue quota or rate limit; a large object occupies the single worker thread for minutes. |
| A stuck run after a crash, restart or database outage; cancellation that never takes effect | Worker liveness | Heartbeats; stale-run recovery that re-checks staleness; graceful release on shutdown; cooperative cancellation at each heartbeat; a database error records nothing | `test_a_stale_running_run_returns_to_the_queue_and_then_completes_exactly_once`, `test_recovery_never_touches_a_healthy_worker_that_is_really_running`, `test_a_queued_run_survives_a_backend_restart`, `test_a_running_run_left_by_a_crashed_process_is_recovered_by_the_next_one`, `test_a_database_error_during_execution_records_nothing_and_leaves_the_run_recoverable` | A run that crashes its worker every time is retried each time (no attempt counter). |
| Wording that implies authenticity, manipulation or origin | Observation text, Method metadata, API and UI copy | Output contract rejects conclusion vocabulary in every statement and in Method metadata; disclaimers are authored and pinned; the UI keeps Observation, Finding, Claim and Assessment apart | `test_the_output_contract_rejects_conclusions`, `test_the_real_method_never_emits_conclusion_vocabulary`, `test_user_facing_examination_copy_states_measurements_never_conclusions`, and the frontend test `never states a conclusion about authenticity, manipulation or origin` | Free-text evidence labels and filenames are user data and are displayed as escaped text only. |
| An examination changing Evidence, an EvidenceObject, custody history or stored bytes | Everything the examination touches | The only writes are `analysis_runs`, `observations`, `audit_events` and `identifier_sequences`; no Finding, Claim, Assessment or relationship is created | `test_examination_leaves_evidence_custody_and_bytes_exactly_as_they_were` (SQL-level), `test_examination_never_creates_findings_claims_assessments_or_edges` | A party with write access to the evidence volume can still change bytes; VERITAS detects it at the next verification or examination but does not prevent it. |

## Authorization model actually enforced

- A User must be active, hold an active Organization membership, and have an assigned Role.
- Role capabilities are defined once in `backend/app/domain/roles.py`; the database Role catalog stores role identities only.
- Case access additionally requires a matching case-scoped RoleAssignment, except an out-of-band provisioned Auditor assignment carrying `case:read:any` within its Organization membership.
- Parent Case authorization happens before exposing child resources; Evidence/Profile, Evidence intake/Object detail, custody, Findings, Claims, graph, Examination reading (`examination:read`) and execution (`examination:execute`, INVESTIGATOR and RESEARCHER only, authenticated, non-demonstration Cases only) and case Audit each have an explicit capability requirement. EvidenceObject detail requires `evidence:read`; registration/upload requires `evidence:intake`; finalization requires both `evidence:intake` and `custody:write`; custody history requires `custody:read`.
- `ADMINISTRATOR` is not implicitly a Case reader. `AUDITOR` may read Cases in its Organization only according to its explicit organization-scoped Auditor assignment. Browser navigation is a usability reflection of these rules, never their enforcement point.
- V1 demonstration access is a separate, anonymous, read-only adapter permitted only in `development`/`test`; a supplied invalid or expired session cookie does not downgrade to demo access. Production rejects `demo` configuration.

## Organization-scoped security Audit residual boundary

`AuditEvent.organization_id` is the authoritative association used by the security-audit query.
Case events inherit their Case's Organization; identity/admin events carry the affected
Organization, and user-attributed events inherit scope only when exactly one active membership
is unambiguous. Unknown-login failures, anonymous/system events without a target Organization,
and events for users with multiple active Organization memberships can remain `NULL`-scoped.
They stay in the canonical append-only AuditEvent stream but are excluded from every
organization-scoped `/api/v1/admin/security-audit` response. V2 has no platform-wide event reader;
platform operators therefore cannot retrieve those NULL-scoped events through this API.

## Verification boundaries

The automated backend suite uses SQLite by default. Its ORM immutability checks are real, but PostgreSQL trigger tests are skipped unless tests run with `VERITAS_TEST_DATABASE_URL` pointing at PostgreSQL (CI does this). V2.2 was additionally run against PostgreSQL 17 and through a disposable Docker Compose project (`scripts/qa/v2_2_runtime_check.py`: health, backend-only evidence volume, retrieval and verification over HTTP through nginx, large-object streaming, tamper, missing and unreadable objects, database outage, restart persistence). Those runs establish behavior in that environment only. External OIDC/MFA integration, reverse-proxy TLS, production secrets management, distributed rate limiting, penetration testing, and browser/device security reviews are not asserted by these tests.
